# Build and Commissioning Story

**Source material:** three raw issue logs (71, 87, and 154 entries — 312 total, overlapping snapshots of the same history, not independent audits) plus the full technical detail of `SCOPE_TRIGGER_DEBUG_LOG.md` (kept, not deleted — read that file directly if you want the entry-by-entry SCPI-level record; this document tells the story it's the record of).

This isn't a catalog. The three source logs, read straight through, are 312 near-duplicate "Issue / Impact / Resolution" entries — useful as a reference, exhausting as a read, and they hide the actual shape of the project: a handful of real struggles, each with a wrong turn or two before the real fix. This document is organized around those struggles instead — what was actually hard, what was tried that didn't work and why that matters, and what the real fix turned out to be. Routine one-off mistakes (a mistyped placeholder, a stuck pager) are compressed to a single paragraph at the end rather than given equal billing with a four-week debugging investigation.

---

## 1. Getting the Pi to be a trustworthy base

Before any hardware work, the Pi itself produced a run of small, compounding surprises: it was running Debian 13 Trixie / Python 3.13.5, not the planned Bookworm / 3.11 baseline (resolved by running the full test suite as the actual compatibility proof, not by assuming it). The real project lived on `development`, not `main` — an easy branch to clone wrong. GitHub no longer accepts password auth over HTTPS, so pushing from the Pi required generating an SSH key and switching the remote. None of this was hard, but all of it had to happen before anything else could.

The one genuinely non-obvious bug in this phase: `python3-lgpio` was installed system-wide, but the project's isolated virtualenv couldn't see it, so GPIO Zero silently fell back to `NativeFactory` — an experimental backend that worked fine for a quick manual pulse test and would not have been trustworthy for a multi-day endurance campaign. The fix (symlinking `lgpio.py` and the compiled ARM64 extension into the venv) was simple once found, but the failure mode — "it works, just not on the backend you think it's using" — is the kind of thing that only shows up if someone thinks to check which factory GPIO Zero actually selected.

The other recurring gotcha: the Pi's `/tmp` is a 1 GB tmpfs, while the project's own disk-space safety guard requires 2 GB free. Every sequencer-based test halted with `persistence:insufficient_disk_space` — on a Pi with ~51 GB free on its actual root filesystem. The bug wasn't the guard; it was that `/tmp` and `/` are different filesystems with wildly different capacity, and the fix (`TMPDIR=$HOME/ccid_test_tmp`) is now baked into the operator preflight runbook so nobody has to rediscover it.

## 2. Building a rig that can't hurt itself

The electrical build has one throughline: **the ZX-517 driver boards have no onboard flyback protection**, confirmed by inspection rather than assumed from the board's marketing copy. This is the worst possible failure mode available in the whole design — a MOSFET driving an inductive contactor coil without flyback suppression will avalanche-stress on turn-off and typically fail *shorted*, and a shorted K3 driver means leakage injection stuck permanently closed, defeating the pulldowns, the normally-open contactor, and the software 300 ms backstop all at once, with no software remedy once it's happened. Everything else in this section exists in service of making sure that never happens.

Fitting the flyback diodes (1N5404s, chosen for headroom over the originally-suggested 1N4007) surfaced a run of measurement confusions that are worth recording because they'd fool anyone: an in-circuit diode reading of ~0.026 V and beeping in both directions looked exactly like a shorted or reversed diode, but was actually the ~26 Ω coil sitting in parallel and stealing the meter's test current — the only valid test is with one diode leg lifted clear of the coil (which then reads the expected ~0.5 V forward, open reverse). The same "meter current lights up something that looks like a fault" pattern showed up independently when checking for gate pulldowns: continuity-mode testing between `TRIG/PWM` and `GND` lit the driver board's indicator LED, which looked like a solder bridge until resistance-mode measurement (~10 kΩ, confirming a real pulldown) showed it was just the tester's own current.

K3's coil turned out to have different wire colors from K1/K2's (white pair instead of red/black, no polarity markings) — resolved by measuring resistance to identify the coil pair (26.2 Ω) versus the separate normally-open auxiliary-contact pair, then diode-testing both directions to confirm the coil was effectively nonpolarized before assigning and physically labeling positive/negative leads. That labeling work — every contactor, every driver, every supply, every coil lead — wasn't administrative overhead; three visually near-identical assemblies is a real failure mode on its own. Swap K3 with a mains contactor and you get 6,000 clean-looking no-trip results with no obvious cause, because the leakage bank is injecting into an unpowered EVSE.

The remaining open items from this phase are still open, not solved: **K1/K2/K3 physical-state readback** (the software only ever knows what it commanded, never what actually happened — deliberately deferred past the current commissioning stage) and **protective-earth continuity monitoring** (no isolated PE sensing exists; a PE fault is only inferred indirectly, after the fact, when the scope never triggers).

## 3. The oscilloscope's four-week mystery

This is the real story of the project — the longest-running, most instructive struggle, and the one where the eventual root cause turned out to have nothing to do with the oscilloscope at all.

**The symptom, stated plainly:** for weeks, real energized cycles armed the scope, closed K3, and got nothing. The scope stayed in Single, `Trig'd?` never lit, the trace stayed flat, and the cycle timed out and halted as `rig:scope_never_triggered_or_acquire_timeout` — over and over, on a rig that had otherwise been fully commissioned (GPIO, camera, ROI, analysis all working).

**First hypothesis — trigger mode.** Code review found `configure_for_cycle()` sending `:TRIGger:EDGE:*` parameters without ever explicitly setting `:TRIGger:MODE EDGE` first — and on Keysight scopes, edge parameters are inert unless edge mode is actually selected, otherwise the scope just keeps whatever mode (Pattern, Glitch, whatever) was last active on the front panel. This looked like a near-perfect explanation: it would explain why manual front-panel Single presses seemed to work (front-panel navigation sets Edge mode as a side effect) while fully automated runs never did. Fixed, tested live. **Did not fix it.** Readback confirmed `:TRIGger:MODE?` correctly returned `EDGE`, every other setting looked correct, and the scope still never triggered. A real bug, worth having fixed — just not the cause.

**Building the ability to see anything at all.** At this point every failed cycle was throwing away all evidence of what the scope actually saw — no screenshot, no register state, nothing. Adding that capability nearly ended the investigation early: a de-energized dry run of the first timeout-diagnostics implementation *wedged the scope's USBTMC interface badly enough that only a full physical AC power cycle recovered it* — every scope operation started failing with `Errno 110: Operation timed out`, and neither USB reconnection, a scope power cycle, nor a Pi reboot fixed it; only removing AC power from the scope itself for 60 seconds did. The lesson that came out of this shaped everything after: **diagnostics must never run while the rig is still energized**, and the sequencing was corrected so diagnostics only ever fire after full safe-off (K3, K2, K1 all confirmed open).

Even the corrected version had one more trap: a per-query timeout implemented via a daemon thread that gave up waiting on a slow query — but the *thread itself* stayed blocked inside libusb in the background, and when the main thread went on to touch the same connection (including eventual disconnect), the two raced at the C-library level and **the process segfaulted**, wedging the scope again and requiring another cold power cycle. Fixed by removing threading entirely in favor of PyVISA's native synchronous per-resource timeout, which bounds the actual transport call rather than how long Python is willing to wait for it — plus marking a connection permanently unusable after any query failure, so nothing downstream can touch a transport whose state can no longer be trusted. This is the point where diagnostics finally became safe to actually use.

**Second hypothesis — probe ratio ordering.** A focused code review (not another live trial) found `configure_for_cycle` sending `:CHANnel1:SCALe`/`:OFFSet` *before* `:CHANnel1:PROBe` — and on Keysight scopes, scale/offset are interpreted "at the probe tip" using whatever probe ratio is already active when they're sent. Setting them first applies them against a stale ratio, silently misscaling the digitized range while every settings readback still looks completely correct — invisible to a readback check, and invisible to `ScopeSim`, which has no probe-ratio-to-scale physics to get wrong in the first place. This explained a lot: why 300+ passing simulated tests never caught it, why a real burst might appear as only a fraction of its true voltage, why front-panel operation (stateful, ratio already correct from a prior session) "worked" while `configure_for_cycle()` reconfiguring from scratch every cycle hit the bug every time. Fixed, tested live. **Also did not fix it.** `operation_condition` stayed at the "just armed" value for the entire acquisition window; the scope simply never triggered.

**Ruling out the channel path entirely, and finding a real unsupported command.** With channel-side settings now confirmed correct on live readback, attention moved to the trigger comparator itself, which watches a different signal path than what gets digitized. Trigger coupling was set explicitly to DC (separate from channel coupling), `:TRIGger:NREJect OFF` was added to disable trigger noise-reject hysteresis, and an `*OPC?` synchronization barrier was added so configuration couldn't still be in flight when arming began. One of these three turned out to be flatly unsupported on this specific MSO-X 2014A: `:TRIGger:NREJect` returned `-113,"Undefined header"` in the real error queue. An interim fix that discarded configuration errors and proceeded anyway was tried, recognized as the wrong instinct, and reverted — if the scope rejects a configuration command, the resulting state is only partially known, and continuing to arm and inject leakage current against an unconfirmed configuration is a bigger risk than just halting the cycle. `NREJect` was removed outright; any future configuration rejection now blocks the cycle instead of being silently absorbed.

**Instrumenting the actual trigger event, not just the acquisition state.** The operation-condition register (the thing being polled this whole time) answers "is the acquisition subsystem running," not "did the trigger comparator ever actually fire" — those aren't the same question. `:TER?`, the trigger event register, answers the second one directly. Reading it at the moment of a real timeout showed `trigger_event_register = +1` — evidence the comparator *had* fired even though the acquisition subsystem never reported Stop, a materially different condition from a genuine no-trigger and one the single generic halt reason couldn't distinguish. Checkpoints were added at baseline (right after configuration) and again immediately before K3 close, since `:TER?` is documented as read-and-clear (confirmed against the official Keysight programmer's guide) — a fact that immediately caused its own bug: the very first version of the baseline check read `:TER?` once and halted on any nonzero result, which meant it halted on ordinary *stale* residue left over from a prior session just as readily as on a real fault, since a single read can't tell those apart. Fixed with a clear-then-verify pattern — read once to clear whatever's there, read again to actually decide.

**Forcing a look at what the input actually held.** With TER confirmed genuinely zero through an entire K3-closed window on a real cycle — an unambiguous no-trigger, not a hypothesis — a diagnostic-only forced trigger (`:TRIGger:FORCe`, confirmed via the official programmer's guide to be documented since firmware v1.20, well before this unit's v2.43) was added specifically to freeze whatever was on the input into scope memory for inspection, strictly gated on TER already reading zero and explicitly never usable as a measurement verdict. The first real attempt at this froze **a large bipolar burst, roughly −167 V to +141 V** — the most direct evidence in the whole investigation, and very likely the actual leakage waveform, captured for the first time. A follow-on attempt to place that burst precisely in time ("86 ms before K3 closed") turned out to be a mistake of a completely different kind: it mapped a Pi-side `time.monotonic()` timestamp directly onto the scope waveform's own internal time base, and nothing in the system ties those two clocks together. Retracted, and fixed at the tooling level rather than just the one conclusion — a full per-stage Pi-side timeline was added for reasoning about sequence and duration, but any claim about *where in the waveform* something happened was rebuilt to come only from the waveform's own samples and preamble, never from a Pi-side clock.

**The actual root cause, finally — and it was never the scope.** A code review prompted by a very specific observation — "the scope naturally triggered, completed the acquisition, and stopped, and the software still called it a failure" — found the real bug. The acquisition-polling loop used one flag, `forced_diagnostic_attempted`, to mean two different things: "the forced-diagnostic checkpoint ran" and "a trigger was actually forced." It was set to `True` unconditionally the instant the checkpoint ran — *before* checking whether a real trigger had already occurred. On exactly the branch where the checkpoint's own TER gate-read found a real trigger already latched (correctly skipping the force, since forcing would have destroyed real evidence), the outer loop still permanently stopped polling for real completion regardless. So on any cycle where a genuine natural trigger happened to land at or after the ~100 ms checkpoint and then completed normally — the actual desired outcome, the thing four weeks of hardware debugging was trying to produce — the software discarded it and reported a rig fault anyway. This had been quietly eating real successes throughout much of the investigation, alongside whatever fraction of the failures were genuinely electrical. Fixed by gating "stop polling for real completion" on whether forcing *actually happened* (`force_command_return_monotonic_s is not None`), not on whether the checkpoint merely ran. After this fix, natural captures became repeatable.

**The resolution the debug log itself never got to write down.** `SCOPE_TRIGGER_DEBUG_LOG.md`'s own status section still frames this as open as of that fix, with most preceding entries marked "untested against real hardware." It wasn't left open — a real 25-cycle campaign ran and was archived shortly after (`7a15241`), and the operator preflight runbook that now exists treats real V3 campaigns as routine, not aspirational. Four separate, individually real hardware-adjacent bugs got found and fixed along the way (trigger mode, probe-ratio ordering, the `NREJect`-unsupported config-error handling, and the USBTMC/segfault diagnostics hardening) — none of them was the actual cause, and the actual cause was a state-tracking bug in code that had nothing to do with the electrical signal chain at all. The lesson explicitly recorded at the time is worth keeping verbatim: **audit control-state flags before changing proven electrical settings.**

A few smaller, real findings ride alongside this story rather than inside it: a genuine safety-relevant bug where K3 could stay closed for the *entire* ~5-second scope acquisition timeout instead of the 300 ms hard backstop, because the real scope's blocking wait call prevented the outer loop from ever rechecking the K3 deadline while it was in flight (fixed by polling in short 10 ms slices instead of one long blocking call — the first attempt at 50 ms slices still overshot to ~360 ms because of a stacked outer-loop sleep); and a recurring, explicitly-stated governance rule that came out of repeating the same energized failure more than once without new evidence: **don't repeat an energized attempt hoping for a different result — improve what evidence gets captured first.**

## 4. Teaching a webcam to recognize "the CCID is actually in service"

The vision system's job is narrow — confirm the EVSE reached charging state before K3 closes — but getting it right took two real redesigns.

The groundwork was mechanical: the C270 needs several seconds of active frame reads (not just a sleep) before exposure and gain settle, or every early frame is black; manual exposure resets to automatic on every USB/power reconnect and has to be reapplied every time (locked at 30 initially, later raised to 60 after a rig remount changed the ambient lighting enough that 30 came out dark and purple); auto white balance turned out to be impossible to actually disable on this camera despite the command appearing to succeed, so the fix was to stop fighting it and control the physical environment instead; and the calibrated ROI computed by the calibration tooling was, for a while, never actually wired into the runtime sequencer at all — `calibrate_camera.py` produced a correct `roi.json`, but the real charging gate kept silently using the hardcoded default center ROI regardless, because there was no `vision:` config section carrying it through. Calibration success and runtime behavior were two unconnected things until that was fixed.

**The first real bug: a correct classifier that could still be fooled by real noise.** A live commissioning attempt halted on a stuck-BOOTING vision-gate timeout despite the operator visually watching the EVSE LED flash green. This was reproduced deliberately — injecting a synthetic spurious secondary-hue frame against the real classifier code before touching anything — and confirmed: the temporal window classifier could be tipped from a correct GREEN read into a window-level BOOTING verdict by as few as 2 stray-hue frames out of a ~45-frame rolling window, a real risk from camera noise or glare that clean synthetic green/dark test fixtures never exercised. The fix didn't touch the existing classifier at all — it's kept, unchanged, for FAULTED/READY/OFF/BOOTING diagnostic reporting — but the actual charging-gate *grant* decision was moved to an entirely separate, independent policy based on recent green-frame density.

**The second bug, in the fix for the first bug: granting too early.** The first version of that new policy accepted just three green frames within a two-second window — which the multicolor boot animation's own green phase could satisfy on its own, meaning the sequencer could proceed toward K3 injection before the EVSE was actually charging. Fixed by requiring green evidence to span at least 3.5 seconds within a 6-second window, validated against the real boot-animation's actual shape rather than a synthetic approximation. Two more refinements followed directly from that: the policy initially only cleared accumulated green evidence on a red observation, so a blue reading followed by a short green boot-blip could still contribute toward a false grant (fixed: either red *or* blue clears it), and dark/unknown frames between green flashes needed to preserve prior evidence without ever granting on their own — clearing everything on every dark frame would reject a completely genuine flashing pattern, since flashing necessarily includes dark frames between flashes.

The corrected gate takes roughly 45-50 seconds to grant, which was briefly, reasonably suspected as another bug before being confirmed as correct — it's just the real EVSE boot sequence plus the now-required sustained-green qualification, not a defect. Validated for real by disabling K3's coil supply entirely and running the real camera/GPIO against a simulated scope — a pattern that produces a synthetic PASS that must never be mistaken for real electrical trip evidence, which is exactly why `camera_gate_check.yaml` stays untracked and out of every commit.

## 5. When the algorithm lied — V1 to V2 to V3

The trip-time algorithm's story is really one recurring shape, played out twice: a real defect gets found, gets fixed, and the fix itself needs a second, more targeted fix because the first one was too broad.

**V1's defect:** the leading envelope used to check for pre-trigger leakage looked *forward* into future samples — so later burst energy contaminated the classification of the very first sample, producing false stuck-K3 indications on genuinely clean captures and forcing onset to the record boundary on records where no fully silent forward-looking window existed. The naive fix — just remove the forward-looking check — would have been a real safety regression: it made a deliberately-constructed, genuinely-stuck-K3 test scenario pass when it should fail. The correct fix added a second, narrower raw-sample check over the first quarter-cycle specifically for the boundary case, rather than deleting the protection the first check was (badly) trying to provide. Because this materially changed a real result (one specific real capture moved from 20.1676 ms to 13.5334 ms), it shipped as an explicit new version, `AnalysisVersion.V2` — V1's exact original behavior preserved untouched for historical replay, never edited in place. This is the versioning discipline the rest of the codebase follows for exactly this reason.

**The 25-cycle campaign, and V2's own defect.** With V2 validated and a real campaign underway, Cycle 17 came back as a 33.36 ms FAIL — a result that, taken at face value, meant the DUT had failed its pass limit, with every V2 sanity check reporting clean. It wasn't the device. V2's onset refinement could jump backward by nearly a full mains half-cycle on a single spurious residual-floor noise crossing, and in this case the jump was about 16.8 ms — enough to turn what was very likely a passing trip into an apparent failure. Three other cycles from the same campaign (5, 14, 18) showed the same mechanism at smaller magnitude (still >10 ms backward jumps) and were flagged for the same reason, not dismissed just because they weren't the most dramatic case. The lesson recorded at the time: **a clean sanity-check pass does not by itself prove correct endpoint placement.** Fixed as `AnalysisVersion.V3`, which requires a *sustained* run of consecutive above-threshold samples before declaring onset, instead of trusting a single crossing — V2's results kept exactly as originally computed, for audit history, never overwritten.

Two smaller but real guards came out of the same campaign: a run could show a numerically-plausible PASS while the rig simultaneously halted for an unrelated reason (`k3_pretrigger_current_detected` on the same cycle as a 20.17 ms PASS reading) — meaning a bare pass-count could be badly misread as a fully valid accepted cycle, which forced the rule that a numerical PASS is only ever meaningful alongside every required sanity check being true and no rig halt on that cycle. And an impossible endpoint ordering (`t_end` computed before `t0`) was observed on a real waveform and had been silently clamping to a zero-duration "PASS" instead of being rejected outright — fixed to reject explicitly and preserve the waveform for correction rather than accept a number that can't physically be true.

**Still open:** the first cycle of a run can sometimes produce a real, visible waveform that still analyzes as exactly `0.0 s` — root cause not yet resolved, currently handled by excluding it from performance statistics while preserving it as debugging evidence, and it's an explicit gate in the current operator preflight runbook ("treat first-cycle zero-time behavior as unresolved until fixed"). And V3 has not yet been replayed across the archived 25-cycle dataset — Cycles 5, 14, 17, and 18 specifically remain flagged as suspect under V2's defect until that replay happens, which is exactly why the raw waveforms were kept in the first place rather than just the computed verdicts.

## 6. Networking, unattended operation, and monitoring

Three smaller struggles, tied together by the same underlying goal: make the campaign survive without a human physically present.

**Getting off the iPhone.** Depending on a phone hotspot for the Pi's network access isn't viable for a multi-day unattended run — the phone has to stay connected and available the whole time. Moved to a dedicated Verizon USB-tethered hotspot instead, which took its own round of real troubleshooting (the target SSID missing until a forced rescan, a mid-switch SSH disconnect that required falling back to the still-working iPhone connection, `usb0` briefly confused with `/dev/video0` — unrelated device namespaces that happen to look similar) before landing on a validated setup: confirmed via `ip route get 8.8.8.8` that traffic actually left through `usb0`, not just that a ping happened to succeed, and confirmed route metrics kept the intended interface primary when both networks were briefly active at once.

**Proving systemd actually owns the process.** A campaign started directly in a foreground SSH session is at the mercy of that session — laptop sleep, terminal close, or network loss all silently kill it. `systemd-run` (transient units, not the pre-existing persistent unit) was validated by starting a run, disconnecting SSH entirely, and confirming completion afterward through the journal and the run's own artifacts. This is worth being explicit about: **the persistent, `enable`d service described in `DEPLOYMENT.txt` and `deploy/ccid-automation.service` has never actually been exercised against the real deployment path.** That unit references `/opt/ccid`; the tested, commissioned code has always lived at `/home/ccid/ccid_automation`. Every real validated run to date — five-cycle, twenty-five-cycle, all of it — used transient `systemd-run` invocations pointed at the real path instead. This is the concrete evidence behind the operational-model question `legacy-documentation-audit.md` raises at §2.8: it's not a hypothetical discrepancy between two documents, it's that only one of the two documented deployment patterns has ever actually been used.

**Swapping the dead-man's switch mid-project.** The original monitoring plan (healthchecks.io) was replaced with Cronitor — a preference change, not a bug, but a real amount of integration work followed: persisting the heartbeat URL where a systemd-run invocation would actually inherit it (an interactively-exported shell variable doesn't carry into a service invocation at all), keeping the URL out of chat/git/shell history since it embeds a secret key, and separately proving both the success and failure/recovery delivery paths actually reached Cronitor rather than just trusting the configuration looked right. Uptime Kuma was evaluated and rejected for the same reason a dead-man's switch has to live off the machine it's watching — running it on the same Pi it would be monitoring can't detect that Pi's own power loss. As of the most recent evidence, **the Cronitor monitor has actually been deleted outright** (not paused), which matches exactly what the current operator preflight runbook still says needs revalidating before a long run — this wasn't fixed and then re-broken, it's been open the whole time.

## 7. Everything else — the small, recurring friction

A handful of patterns showed up repeatedly enough across all three source logs to be worth naming once rather than as fifteen separate incidents: compressed one-line Python/shell commands are unusually prone to corruption in transit (copy/paste, terminal wrapping, transcription) and the durable fix was always the same — short commands or small multiline blocks, syntax-checked immediately, never dense one-liners for anything nontrivial. Manual single-line text-replacement edits to source files reliably produced subtly broken code (lost indentation, mangled identifiers, tabs mixed into space-indented files) in ways that were only ever caught by a subsequent compile or test failure, never by inspection — the recovery pattern was always restore-from-known-good plus smaller, controlled edits, not more manual patching. An overly broad `sed` pattern once matched more than its intended target and broke an unrelated code block; the fix, applied afterward as a standing practice, was exact context-aware edits with test-first development for anything nontrivial. And several purely procedural lessons stuck: run tests with the real `CCID_SCOPE_RESOURCE` hidden (`env -u`) so ambient environment state can't change what a test is actually proving; never reuse a run ID, even for an aborted attempt that never completed a cycle; and — stated as an explicit working agreement partway through the project — long, dense multi-step instructions produced more sequencing mistakes during live hardware work than short, one-action-at-a-time steps did.

## 8. The night the campaign learned to heal itself

Two real incidents, in quick succession, on genuinely large unattended runs — 5,800 cycles, then a run reaching past cycle 480 — and both exposed the same underlying gap from two different directions: the software's only answer to almost anything going wrong was to stop the whole campaign and wait for a human to notice.

**Cycle 38, and the traceback that didn't survive.** A 5,800-cycle real campaign (`5800_v3_real_20260813T175531Z`) halted with `controller:unexpected:ValueError` at cycle 38. The Pi became unreachable shortly after and needed a power cycle — and journald, non-persistent by default, took the original traceback down with it. What was left was a theory, not a fact, and the investigation had to proceed on code review alone rather than the actual evidence: `_poll_acquisition_with_backstop`'s per-iteration timeout was computed from a monotonic read taken earlier in the same loop body, one line before a boundary-inclusive `while ... <= acq_timeout_s` guard — two independent clock reads a moment apart, straddling an inclusive deadline, that real scheduling jitter could occasionally let straddle zero, handing the HAL a `timeout_s` it explicitly rejects with `ValueError`. Reachable rarely enough to explain surfacing once in 38 cycles rather than every cycle, which fit the evidence that did exist. Fixed by computing the remaining time fresh, immediately before the call, and simply not calling the HAL at all when it isn't strictly positive — letting the existing backstop/timeout paths handle that iteration exactly like an ordinary timeout. Confirmed with regression tests placing the fake clock exactly on and slightly past the boundary, something the existing suite had never covered.

The more durable fix wasn't the boundary check itself, though — it was closing the actual gap the incident exposed: **nothing durable ever recorded more than an exception's class name.** `Sequencer`'s last-resort exception handler built `controller:unexpected:{ExcType}` and moved on; the message, the traceback, the cycle state at the moment of failure — none of it went anywhere but a log stream that had just proven itself unreliable. Fixed by capturing all of it — type, message, full formatted traceback, last known state, the whole per-cycle transition list, timestamps — into a `diagnostics/<cycle>/controller_exception.json` written through the same fsync'd local-disk path every other diagnostic artifact already uses, deliberately wrapped so a *second* failure trying to record the first one can never mask it. The next unexpected exception, whatever it turns out to be, won't depend on journald surviving a reboot to be diagnosable.

**Then the actual operational question got asked directly: why does this keep stopping overnight?** Every halt category — a scope timeout, that same class of controller bug, disk space, a genuine DUT no-trip — ended the campaign outright and left it idle until someone noticed the Cronitor alert and manually resumed. For an unattended multi-day run, that idle-until-noticed gap was the real source of the "it keeps crashing every couple hours" frustration, not necessarily anything actually being wrong with the rig each time. The fix took real back-and-forth to scope correctly, because the obvious version of it — auto-retry everything — runs straight into a design decision this project made on purpose: halts are sticky specifically so a device that already failed a real test doesn't get silently re-tested for days without anyone knowing. The resolution, after that was argued through explicitly rather than assumed: **auto-retry, but not uniformly.** A `NO_TRIP` — the DUT genuinely failing to clear a fault, the one thing this rig exists to catch — gets a short leash, 3 consecutive occurrences before a human is pulled in. Everything else that isn't a DUT verdict (`RIG_FAULT`, `CONTROLLER`, `PERSISTENCE`) gets 5, on the reasoning that those are far more likely to be transient rig/software flakiness than a marginal boundary case. Either streak resets the moment a cycle actually completes.

Getting the "resets on progress" part right took a second pass: the first version compared `pass_count + fail_count` against a baseline, which looked reasonable and was wrong — `fail_count` counts *any* non-PASS verdict, including a committed `NO_TRIP`, so a `NO_TRIP` would have quietly reset its own streak counter the instant it happened, defeating the entire reason it was given a tighter limit in the first place. Fixed by checking whether more than one cycle appears in the result of a single `sequencer.run()` call instead — a call only ever returns on completion or a halt, so more than one entry there can only mean a real cycle finished first.

And retrying itself surfaced a genuine safety-relevant bug, not a hypothetical one: some halts (a scope that never triggers) occur *after* K3 has already legitimately closed once for that cycle, without ever committing a cycle record — meaning a naive retry at the same cycle number collides with the charging-gate token's single-use-per-cycle interlock and raises `SafetyViolationError`. Caught by writing the regression test that exercises exactly this sequence, not by reading the code and assuming it was fine. Fixed by always advancing past whichever cycle number was actually attempted, whether or not it ended up committed to `cycles.csv` — the interlock had done exactly its job; the retry logic just needed to respect it properly.

**The second incident, a different failure shape entirely: cycles 482, 483, and 484 all reported the camera unavailable immediately, before the vision gate even reached the boot-wait phase.** Investigated directly rather than guessed at: the C270 had re-enumerated from `/dev/video0` to `/dev/video1`/`video2` — a real USB reconnect event, not a software regression — and the hardcoded `device_index: 0` kept dutifully trying to open a device that was no longer the camera. This is a known failure class for this exact hardware (`docs/build-and-commissioning-issue-log.md` §D's earlier "many `/dev/video*` devices" entries already flagged the risk; it had just never actually happened mid-campaign before). Two fixes, addressing two different halves of the same problem:

- **Stop depending on enumeration order at all.** `camera.device_index` now accepts a stable device path alongside a raw index — `cv2.VideoCapture()` already supports both — and a new udev rule (`deploy/99-c270-camera.rules`) matches the camera's own USB serial rather than whichever `/dev/videoN` it happens to land on, creating a fixed `/dev/ccid_camera` symlink. The exact same pattern already proven for the scope (`deploy/99-keysight-usbtmc.rules`), just never extended to the camera until it actually bit.
- **Give the system a way to notice and recover on its own.** `Sequencer` now refreshes the camera and scope connections — a full stop/start, disconnect/reconnect — every 50 cycles on a fixed schedule, and reactively, immediately, after 3 consecutive camera-unavailable cycles rather than waiting for the schedule to catch up (a fixed 50-cycle interval alone would only have caught cycles 482-484 by coincidence). Both triggers fire strictly before mains ever close for that cycle, both are best-effort and swallow their own failures rather than crashing the cycle, and — worth being honest about — neither one can recover a scope already marked permanently unusable after an unrecoverable diagnostics timeout; that flag is set once and never cleared, on purpose, and this refresh isn't trying to be smarter than it.

Both incidents together validated with 364 tests, up from 349 at the start of this arc — including, notably, tests that were only added *after* being wrong the first time (the progress-detection bug, the retry-collision bug) rather than tests that happened to catch things on the first attempt. Neither fix has yet been proven against a repeat of the exact failure it targets on real hardware — that's the honest status, not a claim of resolution.

## 9. Still open going into the 6,000-cycle campaign

The authoritative current list, cross-checked against `legacy-documentation-audit.md` §4 and the current operator preflight runbook — not the stale "NOT RUN - HARDWARE REQUIRED" framing still sitting in `IMPLEMENTATION_STATUS.md`:

1. **K1/K2/K3 physical-state readback** — deliberately deferred, not solved.
2. **Protective-earth continuity monitoring** — no isolated PE sensing exists; only indirect consequence detection.
3. **First-cycle zero-time analysis behavior** — root cause not confirmed fixed; currently handled by manual exclusion, not a software fix.
4. **V3 replay across the full archived 25-cycle dataset** — Cycles 5, 14, 17, and 18 specifically, all flagged under the V2 onset-refinement defect.
5. **Campaign-level statistical acceptance criteria** — deliberately deferred to offline engineering review, per `handoff_latest.md` §16's own explicit non-goal; still has to actually happen before 6,000 cycles can be judged as a whole.
6. **UL 2231-2 endpoint definition confirmation** — same open item as `IMPLEMENTATION_QUESTIONS.md` #2.
7. **Off-Pi automatic backup** — one manual selective backup exists (the 25-cycle archive); nothing automatic exists yet for a much larger campaign's worth of data.
8. **Permanent systemd service installation** — every real validated run to date, including the 5,317-cycle campaign this documentation update accompanies, used transient `systemd-run`; the persistent-service path has never itself been exercised.
9. **Cronitor monitoring lifecycle** — was reset and reconfirmed as part of getting the 5,317-cycle campaign running, but the full lifecycle discipline (schedule/grace/alert/pause-resume all deliberately revalidated, not just "a monitor exists") from the operator runbook's own gate is not independently confirmed done.
10. **Full watchdog, reboot, and power-loss/sticky-halt-resume commissioning** — SSH-independence is proven; hardware watchdog, kernel hang, and true power-loss recovery are not.
11. **Auto-retry and equipment refresh, unvalidated against a repeat real-hardware incident** — both shipped in response to real failures (§8), both pass their regression tests against simulated hardware, but neither has yet been proven to actually recover the exact real-world condition it targets (a genuinely wedged camera reader thread; a scope that would have kept timing out without the retry). The next time either failure mode recurs is the real test.

The operator preflight runbook's §16 "Long-Campaign Gate" is the living, current version of this list — this section exists to carry the *reasoning* behind each item, not to duplicate the runbook's own checklist.
